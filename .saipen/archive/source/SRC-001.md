## Request

ZAICODE

ROLE

You are the implementation and integration agent.

Build the first working ZAICODE foundation on top of the current official upstream ZCode source repository:

https://github.com/zai-org/ZCode

This is a multi-milestone autonomous implementation handoff.

Do not stop after repository installation or after producing an architectural report. Continue through the milestones sequentially while eligible work remains.

Do not ask for "continue?" between normal milestones.

Stop only for a genuine hard blocker:

* required operator credential or interactive authentication that cannot be completed safely;
* destructive migration requiring explicit operator approval;
* upstream integrity or licensing problem;
* missing dependency that cannot reasonably be installed;
* architecture discovery proving that the requested integration cannot be implemented without replacing a major upstream subsystem.

PRIMARY GOAL

Use ZCode as the technical foundation for ZAICODE.

ZAICODE should evolve into a local coding-agent workspace where multiple named agents can be configured, observed, assigned work, queued, resumed, and eventually orchestrated from one UI.

The first implementation must establish:

1. isolated local ZAICODE source installation;
2. verified upstream development environment;
3. architecture map of the existing ZCode agent/subagent/task/queue/runtime systems;
4. ZAICODE-specific UI product contract in root `UI.md`;
5. first ZAICODE agent-management layer using existing ZCode primitives wherever possible;
6. first useful Agent Queue UI;
7. persistent agent definitions and observable execution state;
8. clean verification and continuation state for future work.

UPSTREAM BASELINE

Treat the currently cloned official `zai-org/ZCode` main branch as the source of truth unless repository metadata clearly indicates another supported development branch.

At the beginning, record:

* upstream repository URL;
* current branch;
* exact commit SHA;
* package version;
* Node version required by `mise.toml`;
* pnpm version required by `mise.toml`;

INSTALLATION SAFETY

The user already uses ZCode.

Do not overwrite, uninstall, corrupt, reset, migrate, or repurpose the user's existing production ZCode installation or account configuration.

Do not destructively modify existing ZCode runtime state under the user's profile.

The development source checkout and the installed production ZCode application must be treated as separate systems.

Do not reuse production databases for development tests when an isolated test database or profile can be used.

Do not expose secrets, OAuth tokens, API keys, account identifiers, or credentials in repository files, logs, fixtures, screenshots, or documentation.

MILESTONE 4 — CREATE ROOT UI.md

Create:

`UI.md`

This file is the ZAICODE product-interface contract.

It supplements upstream `DESIGN.md`; it does not replace or duplicate the design system.

`DESIGN.md` remains authoritative for component styling, typography tokens, colors, themes, spacing, responsive behavior, accessibility conventions, and supported platform behavior.

`UI.md` must define ZAICODE-specific information architecture and operator workflows.

At minimum include:

# ZAICODE UI

## Product Purpose

ZAICODE is an operator-oriented multi-agent coding workspace.

The UI should make agent state, queued work, active execution, blockers, results, and ownership obvious without forcing the operator to open multiple dialogs.

## Core Principles

* one primary workspace;
* dense but readable;
* desktop-first;
* minimal modal interaction;
* keyboard-friendly;
* no unnecessary combobox-heavy configuration;
* critical execution state always visible;
* explicit agent ownership;
* explicit queue state;
* explicit blocked state;
* explicit provider/model identity;
* no hidden destructive actions;
* persistent operator context across restart.

## Main Workspace

Define the intended main-screen regions:

### Navigation / Workspace

Project/workspace selection and high-level ZAICODE navigation.

### Agent Roster

Visible list of configured agents.

Each row/card should expose:

* name;
* role;
* status;
* model;
* provider;
* current job;
* queue depth where applicable;
* last activity;
* error/blocker indicator.

### Work Queue

Operator-facing ordered task queue.

Required task states:

* Draft
* Queued
* Ready
* Running
* Waiting
* Blocked
* Completed
* Failed
* Cancelled

Do not add states that the runtime cannot actually distinguish.

### Active Work

Show currently executing agent jobs and meaningful progress/runtime events.

### Inspector

Selected agent/job details without forcing navigation away from the queue.

### Event / Result Surface

Readable execution results, important tool events, errors, and completion summaries.

## Agent Management

Specify:

* Create Agent;
* Rename Agent;
* Edit Role;
* Edit Instructions;
* Choose Provider;
* Choose Model;
* Enable/Disable;
* Duplicate;
* Delete;
* Run;
* Pause only if runtime supports real pause semantics;
* Cancel;
* Queue Task.

Do not implement fake Pause if the engine only supports Cancel.

## Queue Interaction

Specify:

* add task;
* edit pending task;
* reorder eligible tasks;
* dispatch;
* cancel;
* retry failed;
* resume blocked task when possible;
* inspect history;
* filter by agent/status/workspace;
* preserve queue across application restart when persistence is supported.

## Agent Status Vocabulary

Use precise runtime-backed states.

Suggested display vocabulary:

* Idle
* Queued
* Starting
* Running
* Waiting
* Blocked
* Completed
* Failed
* Offline

Map every displayed status to an authoritative runtime state.

## Model and Provider Visibility

The UI must make it possible to see which model/provider an agent will actually use.

Do not show a configured model as active when runtime fallback selected something else.

## Permissions

Dangerous or privileged tool actions must respect the existing permission system.

Subagents must not silently gain broader permissions than their parent or configured profile.

## Persistence

Document which ZAICODE UI state is:

* runtime-authoritative;
* persisted configuration;
* local UI preference;
* derived display state.

## Keyboard Workflow

Define useful shortcuts only after checking for collisions with existing ZCode shortcuts.

## Responsive Behavior

Preserve usable Web behavior but prioritize the Windows desktop workspace.

## Non-Goals

For the first ZAICODE milestone:

* no distributed multi-machine scheduler;
* no arbitrary agent nesting;
* no visual node editor;
* no complex DAG workflow engine;
* no autonomous infinite execution;
* no replacement of ZCode's model/provider stack;
* no rewrite of the terminal;
* no replacement of upstream permission architecture.

MILESTONE 7 — ZAICODE WORK QUEUE

Implement the first operator-facing ZAICODE queue.

First inspect whether ZCode already has an authoritative execution/background-task queue suitable for extension.

If yes:

* expose and extend it instead of duplicating state.

If no:

* create a minimal durable queue service at the appropriate service layer.

Minimum job model:

* id;
* workspace identity;
* agent ID;
* title;
* task/instructions;
* status;
* priority or explicit ordering;
* created time;
* started time;
* finished time;
* result summary;
* error/blocker reason;
* associated session/run identity;
* retry lineage where applicable.

Required invariants:

* a job has one authoritative owner;
* the same queued job cannot be dispatched twice accidentally;
* restart does not silently convert Running into Completed;
* stale runs cannot overwrite a newer retry;
* cancellation is idempotent;
* completion is idempotent;
* retries create traceable lineage;
* workspace identity is preserved;
* task ordering is deterministic;
* UI state is not treated as execution truth;
* completion notification failure must not silently lose terminal job state.

Prefer explicit lifecycle transitions over booleans.
