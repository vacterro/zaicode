# ZAICODE SAIPEN облачный транспорт

Как этот checkout и сессия Claude Code Cloud запускают один воркспейс SAIPEN
с разной локальностью исполнителей и где их граница.

## Форма

```
  local machine                                  Claude Code Cloud
  ────────────                                   ─────────────────
  ZAICODE checkout                               ephemeral checkout
  branch saipen-live                             branch saipen-live
       │                                                │
       └────────── origin/saipen-live ─────────────────┘
                        (github.com/vacterro/zaicode)
```

Одна ветка несёт состояние протокола. Ни шага слияния, ни шага rebase
и ни второй локальной ветки для синхронизации: кто из исполнителей
имеет проверенный чекпоинт — коммитит и пушит, другая сторона
забирает его fast-forward.

`master` — история до переноса и опубликованная ветка по умолчанию. Транспорт
не обновляет её принудительно.

## Что переносится, а что нет

Чекпоинт в этом репозитории несёт состояние протокола SAIPEN, корневой
лаунчер, установщик, документацию и эти транспортные скрипты. Это весь
слой воркспейса.

Он несёт **ни одного байта продукта**. `zcode/` — отдельный репозиторий Git,
указан в `.saipen/source-nested-repos.json` и в gitignore в корне
(`/zcode/`). Для работы над продуктом нужен собственный клон `vacterro/zaicode` на ветке
`zaicode`, и этот клон — второй независимый объект со своей историей.

Следствие легко перепутать: чистый `git status` в этом корне ничего не говорит
о незакоммиченной работе над продуктом, а fast-forward `saipen-live` ничего
не говорит о коде продукта. Проверяйте `git -C zcode status` явно.

## Локальная половина

Два скрипта, оба принадлежат репозиторию — новая машина получает их
из репозитория, а не из памяти:

| Файл | Роль |
|------|------|
| `tools/saipen-cloud/Install-SaipenLiveSync.ps1` | валидирует, сверяет ветку, ставит и запускает вотчер, пишет запись автозапуска, доказывает local == remote |
| `tools/saipen-cloud/ZaicodeSaipenLiveWatcher.ps1` | цикл: fetch, сравнение, fast-forward или push, лог, пауза; затем продуктовый проход и самообновление |
| `tools/saipen-cloud/Test-SaipenLiveSync.ps1` | round-trip с независимым исполнителем плюс доказательство восстановления после холодного старта |
| `tools/saipen-cloud/Test-ProductSync.ps1` | продуктовый проход и самообновление на одноразовых Git-репозиториях (без сети, без реального remote) |


Установка и починка:

```
powershell.exe -File tools\saipen-cloud\Install-SaipenLiveSync.ps1
```

Идемпотентно. Локальное состояние машины живёт в `%APPDATA%\SAIPEN`:
`ZaicodeSaipenLiveWatcher.ps1` (копия), `ZAICODE_cloud-sync.log` (ротируется на
2 МБ в `.log.1`), `ZAICODE_cloud-sync.lock` (единственный экземпляр),
`ZAICODE_cloud-sync.pid` и запись в папке Startup
`SAIPEN-ZAICODE-Cloud-Sync.cmd`.

Установщик отказывается работать с грязным деревом и никогда его не чистит. Если
все грязные пути — каноническое состояние SAIPEN внутри `.saipen/`, он
сообщает об этом и печатает точные команды для чекпоинта; это
незакоммиченное состояние протокола, а не сбой транспорта, и установщик
не станет коммитить его за спиной у протокола.

## Поведение вотчера

| Ситуация | Действие |
|-----------|------|
| чисто, local — предок remote | `git merge --ff-only` |
| чисто, remote — предок local | `git push` |
| грязно | пауза; даже fetch не делается |
| другая ветка | пауза |
| оба продвинулись, общего предка нет | пауза, лог обоих commit id, ничего не мержим |
| fetch или сеть упали | лог degraded, повтор на следующем тике |
| merge/rebase/cherry-pick в процессе | пауза |

Никогда: force push, hard reset, stash, clean, checkout чужой ветки,
commit или остановка по имени процесса. Установщик останавливает вотчер
только по pid, который сам записал в свой pid-файл.

Грязное дерево не стоит ничего: вотчер проверяет грязь до fetch.
Поэтому простаивающий checkout вообще не делает сетевых вызовов.

### Продуктовый проход (T-90)

`zcode/` — самостоятельный репозиторий, так что таблица выше никогда не
двигает код продукта. После него тот же тик обрабатывает checkout продукта
(`-ProductRepo`, по умолчанию `<repo>\zcode`; ветка `-ProductBranch`, по умолчанию `zaicode`).
Продуктовый проход выполняется независимо от того, грязное ли внешнее дерево.
Он только тянет (pull).

| Ситуация | Действие |
|-----------|------|
| удалённая впереди, ни один входящий файл здесь не изменён | `git merge --ff-only`; незакоммиченная работа над продуктом остаётся как есть |
| удалённая впереди, входящий файл здесь изменён | HELD: записать файлы, ничего не сливать |
| локальная впереди | записать; **никогда не пушить** (продукт публикуется через SAIPEN SHIP) |
| расхождение | пауза, записать оба id, ничего не сливать |
| другая ветка, идёт git-операция, fetch не удался | пауза |
| нет checkout `zcode/` или `-NoProduct` | пропущено |

git сам отказывается делать fast-forward, который перезаписал бы локальное изменение, поэтому проверка HELD — более ранняя и понятная защита, а не единственная. Product fast-forward ничего не пересобирает: чтобы проверить, выполните `pnpm bundle:zaicode` (или dev preview).

### Самообновление (T-90)

Наблюдатель работает как копия в `%APPDATA%\SAIPEN`, поэтому более новый наблюдатель в репозитории никогда не запускался без переустановки. В режиме цикла он теперь при каждом проходе сравнивает свой файл с закоммиченной копией в репозитории. Эта копия устанавливается поверх него самого, и он перезапускается ровно один раз с теми же аргументами, только если выполнены все условия:

- два файла различаются;
- копия в репозитории без незакоммиченных правок;
- копия из репозитория парсится без ошибок.

Копия, которая не парсится, отклоняется и пишется в лог, работающий наблюдатель продолжает работу.

Наблюдатели, установленные до T-90, не имеют ни product pass, ни самообновления. Выполните `Install-SaipenLiveSync.ps1` один раз на такой машине; после этого наблюдатель обновляет себя сам.

## Облачная часть

`CLAUDE.md` в корне — правило входа, `.claude/skills/saipen/SKILL.md` — процедура выполнения. Навык загружает ядро SAIPEN из `github.com/vacterro/saipen` и запускает его через объявленную поверхность движка `tools/saipen.py`. Ядро закреплено коммитом (`3088eff`), а не тегом. Тег `v8.0.1` — старое ядро с тем же `VERSION`; его `validate` изменяет состояние, а его валидатор отклоняет эту доску.

`STATE.saipen_home` записывает путь ядра того исполнителя, который последним сделал чекпоинт. В облаке первый `saipen continue` на ядре `3088eff` сходится к работающему ядру как одна запись в журнал `DEC` (E-1410). На машине оператора указатель приходит мёртвым так же. Ядро с автосходимостью восстанавливает его при `continue`; иначе выполните `saipen rebind-home --auto`.

**Обратный путь наблюдается.** E-1562 (облако) свёл указатель к `/home/user/zaicode/.claude/saipen-protocol`; E-1571 (машина оператора) свёл его прямо обратно к `V:/.../_SAIPEN`, автоматически, без ручного `rebind-home`. Оба направления — одно и то же автоматическое схождение, поэтому ожидайте один `saipen_home` `DEC` на каждое переключение локали и считайте это ожидаемым шумом, а не дефектом. Это остаётся шумом, пока P1-2 (`docs/HANDOFF_SAIPEN_CROSS_PLATFORM.md`) не выведет указатель из версионированного состояния; не реализуйте P1-2 как побочный эффект того, что вы заметили его. Никогда не правьте указатель вручную.

`STATE.saipen_home` может указывать на рабочую копию ядра **для разработки**, опережающую пин, а не на чистый клон `3088eff` — на машине оператора это ветка `accepted-debt-rebind` с незакоммиченной работой. Ядро не на закреплённом коммите не обязательно неверно, но и чистым источником не является, поэтому правило о голосовом контракте ниже применяется к нему в полной силе. Никогда не коммитьте, не стэшьте, не сбрасывайте, не переключайте и не чистьте ничего в такой рабочей копии; целевое восстановление одного файла `saipen/STYLE.md` — единственное допустимое исключение, и только если оператор об этом попросил.

### STYLE.md — не локальная настройка

`saipen/STYLE.md` должен быть **побайтово идентичен файлу закреплённого ядра** на каждой машине, в каждой копии, без исключений и без локальных правок. На машине оператора копий больше одной:

- рабочая копия ядра в `STATE.saipen_home` (клон Git, на машине оператора — рабочая копия для разработки);
- `%LOCALAPPDATA%\saipen\scheduled-source\saipen\STYLE.md`, заполняемый задачей `saipen-inject` по расписанию (`bootstrap/schedule-run.ps1`). Это **не репозиторий Git**, поэтому `git checkout` никогда его не восстановит — единственный путь: повторная синхронизация через инжектор либо прямая запись опубликованного содержимого.

Токен `style_contract` в `.saipen/STATE.md` — хеш текста этого файла (`tools/validate.py`, `style_contract_token`: CRLF нормализован, строка `style_contract:` исключена). Отредактируете `reply_language` в одной копии — токен сдвинется; другая копия и облако, берущие опубликованное ядро, сохранят опубликованный токен, и каждая запись CLI на несовпадающей стороне будет отклонена с `style_contract ... does not match the installed STYLE.md marker`.
Вот и вся проблема: локальная сторона пишет состояние, которое облако записать не может.

**Смена языка ответа — это коммит ядра плюс переприкрепление пина, а не локальная правка.** Меняйте его в репозитории ядра, публикуйте, переприкрепляйте коммит в SKILL.md и обновляйте `STATE.style_contract` через `saipen recover`. Локальная правка `STYLE.md` рассинхронизирует каждую машину, кроме той, где она сделана.

Одна ловушка, которую стоит назвать: опубликованный `bin/saipen` — привязанная к машине обёртка, жёстко задающая абсолютные пути интерпретатора и рабочей копии одного оператора. Она работает ровно на одной машине. Облако должно использовать `python3 tools/saipen.py`.

Ярлыки: `cc` продолжает текущую работу; `cc all <text>` принимает всё сообщение как источник/appends и продолжает каждую подходящую работу. Ни то, ни другое не требует рутинного подтверждения.

## Классификация возможностей

**AVAILABLE_IN_CLOUD** — состояние протокола и слой рабочего пространства. Чтение и
запись `.saipen/`, лаунчер (`tools/launcher/ZaicodeLauncher.cs`), установщик в `install/`,
`docs/`, `CLAUDE.md`, `.claude/skills/`, а также транспортные
скрипты. Git: чтение, коммит, push и fetch в `saipen-live`. Любой
гейт, который является проверкой файла, ревью диффа или текстовой проверкой.

**LOCAL_WINDOWS_ONLY** — гейты, требующие именно этой машины.

| Гейт | Почему |
|------|-----|
| `tools\launcher\build.cmd` | компилирует `ZaicodeLauncher.cs` средствами .NET Framework `csc`; в облачном образе нет Windows SDK |
| packaged Electron E2E (`zcode` desktop, Solo → queue → dispatch) | нужна десктопная сессия и подготовленный профиль провайдера |
| живой 9router | служба Windows на этой машине |
| интерактивный клик-сквозной прогон по десктопу | человек и экран |
| собственные рантайм-кейсы вотчера | вотчер работает только на машине, где лежит чекаут |

Они фиксируются как локальные границы приёмки. Их никогда не
отмечают пройденными только потому, что дифф выглядел правильным.

**SAFE_TO_DEFER** — слой продукта. Облачная сессия может клонировать
ветку `vacterro/zaicode` `zaicode` и работать в ней. Работа над слоем
рабочего пространства не требует работы над продуктом, но требует
клона: `.saipen/source-nested-repos.json` объявляет `zcode/`, и без него
валидатор завершится с ошибкой `source freshness computation BLOCKED -- declared nested
repository is missing: 'zcode'`. Для `pnpm` нужны
закреплённые pnpm 10.33.2 и подготовленное рабочее пространство.
`pnpm bootstrap` на свежем облачном образе — документированный способ
попасть внутрь, а `package.json` продукта уже объявляет его.

Облако способно проверить только те байты продукта, что лежат в
`origin/zaicode`. Дельта продукта, существующая лишь в чекауте оператора
`zcode/`, здесь невидима, поэтому каждый продуктовый гейт для неё
в облаке — NOT RUN, независимо от самого гейта. T-84 — первый
случай (E-1411): его исправление было только локальным, пока
`origin/zaicode` всё ещё нёс код до правки.

**UNSAFE_TO_EMULATE** — всё, что заставило бы локальный гейт выглядеть
зелёным. Не стабуйте сборку лаунчера, не подделывайте запуск
собранного приложения, не переигрывайте записанный результат
`pnpm verify:pre-push` так, будто он только что получен, и не превращайте
«код выглядит корректно» в строку PASS в `.saipen/LOG.md`.

**KNOWN_CLOUD_DIVERGENCE** — соответствие, зависящее от того, где лежит
чекаут. На ядре `3088eff` облачный валидатор сообщает
об FAILах `closure-evidence` (T-47, T-62, T-76, T-78 на момент
написания), которых на машине оператора нет.

Ядро переносит любое событие LOG объёмом более 1024 байт в
`.saipen/recovery/log-detail/` сайдкар. При чтении оно восстанавливает сайдкар
только когда абсолютный путь чекаута совпадает с путём, из
которого он был записан. Поэтому длинный вердикт VERIFY,
записанный на Windows, в облаке нечитаем, и наоборот тоже.

Дефект в ядре, заведён как P1-1 в
`docs/HANDOFF_SAIPEN_CROSS_PLATFORM.md`. До тех пор пока он не приземлится:

- цитировать вердикт облака и классифицировать его как эту границу, по тикетам
  (`SKILL.md` § 6 содержит проверку);
- никогда не переписывать сайдкары, не перепроверять ради зелёного статуса и не патчить
  ядро;
- держать события LOG в пределах 1024 байт с обеих сторон.

Та же привязка к машинному пути блокирует и работу. Базовый уровень долга
до BUILD фиксируется при первом входе тикета в BUILD и перепроверяется при
каждом последующем входе. Поэтому тикет, впервые вошедший в BUILD на
машине оператора, не может войти в BUILD в облаке: переход отклоняется с
`DEBT_SNAPSHOT_FOREIGN_PROJECT`. T-84 — зафиксированный случай: DEBT-000079 был
захвачен на E-1377, а переход отклонён на E-1446. Оставляйте такие тикеты
машине, которая захватила их базовый уровень.

## Расхождение

Если локальная и удалённая ветви перестают иметь общего предка, вотчер
останавливается. Он не делает merge, rebase и не форсирует push. Оба
идентификатора коммитов попадают в лог, исправление `git log --left-right --cherry-pick <branch>...origin/<branch>` вручную,
а результат сохраняется как контрольная точка, как и любое другое изменение.

## Точное действие на стороне облака

### Скрипт настройки окружения (один раз, в настройках облачного окружения)

Меню облачного окружения в заголовке сессии -> Edit -> Setup script. Он
запускается перед каждой новой сессией, поэтому каждая сессия стартует с
готовым продуктовым тулчейном:

```bash
#!/usr/bin/env bash
# ZAICODE cloud toolchain: Node 24 + pnpm 10.33.2 (product gates),
# 9router 0.5.91 (real-router tests), mono mcs (launcher compile check).
set -u
NODE=v24.14.0
if ! command -v node >/dev/null || ! node -v | grep -q '^v24\.'; then
  curl -fsSL "https://nodejs.org/dist/$NODE/node-$NODE-linux-x64.tar.xz" | tar -xJ -C /opt
  ln -sf /opt/node-$NODE-linux-x64/bin/node /opt/node-$NODE-linux-x64/bin/npm /opt/node-$NODE-linux-x64/bin/npx /usr/local/bin/
fi
npm install -g pnpm@10.33.2 && ln -sf "$(npm prefix -g)/bin/pnpm" /usr/local/bin/pnpm
mkdir -p /opt/9router && cd /opt/9router && npm pack 9router@0.5.91 >/dev/null && tar -xzf 9router-0.5.91.tgz
(apt-get update -qq && apt-get install -y -qq mono-mcs) || echo "no mono-mcs: the launcher compile check is NOT RUN"
exit 0
```

### Промпт для каждой новой сессии

Начните сессию на репозитории `vacterro/zaicode`, ветке `saipen-live` и
убедитесь, что агент на машине оператора не пишет в это же время.
Замените последнюю строку на `cc all <new list>`, чтобы передать новую работу.

```
Read CLAUDE.md and .claude/skills/saipen/SKILL.md, then cold-recover SAIPEN
state from .saipen/ on branch saipen-live (STATE.md, BOARD.md, tail of LOG.md).
Chat memory is not state; docs/ZAICODE_SAIPEN_CLOUD.md is the transport contract.

Setup (skip what already exists):
- saipen = python3 .claude/saipen-protocol/tools/saipen.py --project-root <repo root>
  (fetch the kernel per SKILL.md if it is missing); run `saipen rebind-home --auto`
  when saipen_home points at another machine.
- Product clone: git clone -b zaicode https://github.com/vacterro/zaicode zcode
  (gitignored here), then `pnpm install` inside zcode (Node 24, pnpm 10.33.2).
- Real-router tests: export ZAICODE_ROUTER_PACKAGE=/opt/9router/package if it exists.

Rules:
- Fetch origin/saipen-live and origin/zaicode before every commit and every push.
  If the other side moved, merge; never rebase, reset or force. If .saipen/
  histories diverged: keep ours on saipen-live-cloud-<sha>, write both ids to
  .saipen/LOG.md, stop and ask me.
- Product gates in zcode: pnpm typecheck, pnpm lint (0 errors),
  pnpm run architecture:check -- --changed, pnpm test. A gate that cannot run
  here is NOT RUN with the reason; a failure blamed on the environment must be
  shown to fail the same without the change.
- I authorize publishing verified product commits to origin/zaicode and SAIPEN
  checkpoints to origin/saipen-live.
- Nothing is PASS until I test on Windows and say PASS. A finished ticket waits
  in VERIFY with .saipen/evidence/T-###-*.md: its commits and the exact manual
  test steps.
- One writer at a time: if LOG shows the local agent mid-work, stop and ask.

cc
```

На машине оператора вотчер делает fast-forward `zcode` из
`origin/zaicode`; `REBUILD.cmd` (или `REBUILD_fast.lnk`) собирает её, и при
следующем запуске ZAICODE новая сборка подхватывается.
