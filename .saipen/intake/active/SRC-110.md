======================================================================

======================================================================
PHASE 4 — FIRST-RUN BOOTSTRAP
======================================================================

A brand-new Windows profile must be supported.

On first launch, ZAICODE must automatically verify/bootstrap all required managed
components.

The user must NOT need to separately understand SAIPEN or SAIMAIL installation.

Expected startup flow:

ZAICODE starts
-> checks installed managed components
-> initializes missing safe defaults
-> initializes SAIPEN integration
-> initializes SAIMAIL local integration
-> initializes FREE execution path
-> verifies local router/runtime
-> reaches usable UI

This must be idempotent.

Launching ZAICODE ten times must not create ten duplicate services, routers,
protocol installations or mailbox identities.

BOOTSTRAP STATES

Expose understandable product states such as:

Ready
Setting up
Updating
Needs attention
Unavailable

Do not expose internal developer jargon unless the user opens diagnostics.

FAIL-OPEN POLICY

Follow the existing ZAICODE product preference:

If the product can physically launch safely, launch it.

Do not hard-block the whole application because one optional provider,
SAIMAIL peer, translation service or secondary component is unavailable.

Hard-block only where the requested operation is genuinely impossible or unsafe.

PHASE 9 — SAFE AUTO-UPDATE
======================================================================

check
-> download to staging
-> verify
-> stage
-> activate safely

- discard/quarantine bad staged artifact;
- report failure;
- do not brick the application.

- rollback to the last known-good version where architecture allows.

Do not delete the old known-good version until the new one has passed the
required activation boundary.
