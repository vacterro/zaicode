The current supplied archive shows an unrelated SAIPEN protocol-maintenance

SEVERITY

P0:
ZAICODE can degrade after approximately 6-9 hours of continuous operation to
approximately 1-2 FPS and may become effectively unusable.

Observed operator symptoms include:

- severe UI frame-rate collapse after many hours;
- project selection appears to work but the selected project can render an empty
  content area;
- opening projects may stop producing usable content;
- restarting ZAICODE restores normal performance.

This directly violates ZAICODE's primary autonomous-operation purpose.

A program intended to run agents unattended for many hours must not require
periodic application restarts to remain usable.

This request is not satisfied by adding a periodic full application restart.

ROOT CAUSE FIRST.

SECONDARY USER-REPORTED FAILURES

1. When a paid/subscription provider reaches its quota/plan limit, ZAICODE must
   stop repeatedly hitting the exhausted route and automatically fall back to
   SAIFREN according to policy.

2. If the operator changes the selected model/provider after a failure and then
   presses Retry, Retry must use the CURRENT selection.

   Current reported defect:
   GLM reached its limit.
   Operator changed GLM -> SAIFREN.
   Retry still attempted GLM.

3. Antigravity/ZCode rolling quota windows are still not truthful in live use.

   Previous T-143 implemented rolling-window behavior, but the operator still
   observes states such as:
   - "starts at first use";
   - "window started 13 min ago" while no visible active window/countdown exists.

   The operator's intended product behavior is:
   a supported rolling plan window should be actively maintained and visible,
   rather than sitting indefinitely waiting for manual first use.

4. Provider/window state must agree everywhere in the UI.

Do not add unrelated features during this program.

A5. INACTIVE CHAT / SESSION MEMORY BOUNDARY

The operator explicitly notes that completed chats do not need to remain fully
hot in memory forever.

Define a correct two-tier state model:

DURABLE STATE
Stored on disk/service side and recoverable.

HOT RENDERER STATE
Only what is needed for current/recent interaction.

Inactive completed chats/sessions should not keep their complete rendered state
resident indefinitely.

Implement a bounded policy where appropriate:

- current session: fully hot;
- a small recent-session working set: cached;
- older inactive sessions: unloaded from renderer memory;
- reopen: lazily hydrate from durable storage.

Do NOT delete durable conversation history merely to save RAM.

"Not needed in memory" != "delete user data."

Where long message lists remain visible, use appropriate virtualization/windowing
rather than mounting thousands of message/tool nodes.

Do not unload an actively streaming or unsaved session.

A6. BOUNDED CACHES

Audit every cache/history collection for explicit bounds.

Every potentially unbounded cache must have one of:

- LRU/size bound;
- age bound;
- lifecycle invalidation;
- durable backing with hot subset;
- proof that cardinality is naturally bounded.

Pay special attention to project/session caches because the reported failure
appears after long autonomous work.

TRACK B — QUOTA CIRCUIT BREAKER / SAIFREN FAILOVER
======================================================================

B1. ONE AUTHORITATIVE ROUTING DECISION

Inspect the current provider/model execution path.

Do not bolt fallback logic separately into every UI button.

There must be one authoritative effective-route resolver used by:

- composer send;
- Retry;
- auto-continue;
- scheduler;
- prepared tasks;
- subagents/crew where applicable;
- workflow runs;
- background automation.

B2. QUOTA EXHAUSTION CLASSIFICATION

Recognize provider/account exhaustion using structured evidence where available:

- explicit quota telemetry;
- plan limit state;
- authoritative remaining=0;
- resetAt in the future;
- provider-specific quota error;
- HTTP/status error classified as quota exhaustion.

Do not classify ordinary:
- network errors;
- model-not-found;
- auth failure;
- malformed request;
- server 500

as quota exhaustion.

B3. CIRCUIT BREAKER

When a provider/account/plan is proven quota-exhausted:

mark the route unavailable until:

- its known reset time;
- fresh telemetry proves recovery;
- operator explicitly refreshes/re-enables it where appropriate.

While the circuit is open:

ZAICODE must NOT keep hammering the same exhausted route on every task/retry.

The UI should show the route as temporarily exhausted with the known reset.

No noisy repeated provider calls.

B4. SAIFREN FALLBACK

When the selected paid/subscription route is exhausted and SAIFREN is available:

automatically resolve to SAIFREN according to the product fallback policy.

Required behavior:

selected GLM
-> GLM quota exhausted
-> circuit opens
-> effective route becomes SAIFREN
-> task continues without user babysitting.

The transition must be visible/truthful in the UI.

Do not silently claim GLM while executing SAIFREN.

Display something equivalent to:

GLM unavailable until <time>
Using SAIFREN fallback

Keep the user's preferred model selection separate from the temporary effective
route so it can return after quota recovery if policy allows.

B5. ANTI-FLAP

Do not alternate:

GLM -> SAIFREN -> GLM -> SAIFREN

on every poll.

Use the known reset/health state and hysteresis.

When reset occurs, probe/revalidate before routing production work back.

B6. RETRY MUST USE CURRENT SELECTION

This is a separate confirmed bug.

Current reported behavior:

1. GLM attempt fails due to limit.
2. Operator changes selection to SAIFREN.
3. Operator clicks Retry.
4. ZAICODE still retries GLM.

Root cause likely involves a retry object retaining the failed attempt's route.

Trace it.

Define the contract:

RETRY CONTENT
May reuse:
- prompt/task payload;
- attachments;
- relevant run context.

RETRY ROUTING
Must recompute from CURRENT execution selection/policy unless the action is
explicitly named "retry same route".

A normal Retry must not blindly preserve a stale failed provider/model binding.

Tests:

GLM fails
-> select SAIFREN
-> Retry
-> only SAIFREN dispatch occurs.

Also:

provider A fails
-> no manual selection change
-> circuit breaker chooses SAIFREN
-> Retry does not hit A again.

And:

failure unrelated to quota
-> route policy behaves according to normal retry rules.

B7. EXACTLY-ONCE

Fallback must not create duplicate logical turns.

One logical task may have multiple transport attempts, but:
- one visible user request;
- one authoritative active attempt at a time;
- late result from abandoned provider must not overwrite the accepted fallback
  result.

Use stable attempt/run identities.

C2. "STARTS AT FIRST USE" MUST NOT REMAIN FOR SUPPORTED AUTO-ROLLED PLANS

For Antigravity/ZCode plans that ZAICODE is explicitly capable of maintaining:

the product must not sit indefinitely displaying:

starts at first use

while waiting for the user.

At 0% consumption, ZAICODE should initiate the minimal safe window-start action

A start action must be:
- minimal;
- idempotent per window;
- rate-limited;
- attributable;
- safe to retry.

If a vendor cannot actually be started automatically, do not fake a running
countdown. Mark that route truthfully as unsupported for auto-start.

C3. WINDOW STATE MUST SURVIVE SWEEPS AND RESTART

window started at T0

Persist enough state to keep the same real window identity through:
- polling;
- renderer restart;
- ZAICODE restart.

But never carry a stale anchor past a proven reset.

C4. "WINDOW STARTED 13 MIN AGO" BUT NOT VISIBLE

plan.
