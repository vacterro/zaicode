P0 — CANONICAL LIVE EXECUTION TRUTH
REQ-006 + T-234 FOLLOW-UP + CURRENT AUDIT W2-001
==================================================

This is the highest-priority reliability problem.

Known current architecture:

The sessions-index projection can lag behind actual runtime state.

The open conversation publishes an additional live-run signal through the mounted conversation/composer path.

This means some liveness truth is currently dependent on the relevant UI being open/mounted.

That directly matches the user symptom:

- project/session visually appears active
- user switches into it
- only then the UI discovers that execution actually ended

T-234 partially mitigated stale background work by introducing a bounded silence rule around approximately five hours.

That was a tactical repair, not the intended final contract.

The previous handoff explicitly required evidence-based liveness rather than age alone.

CURRENT PROBLEM

A fixed age threshold cannot be authoritative.

A legitimate process may run longer than five hours.

A dead process may become stale after five seconds.

The UI must not infer execution truth from:

- whether a conversation is mounted
- whether the user recently opened the project
- an arbitrary old-enough timer alone

REQUIRED REPAIR

Create or complete a runtime/service-owned liveness contract.

The durable/runtime execution layer must expose enough canonical state to answer:

- is this work still owned by a live runtime?
- when was liveness last positively confirmed?
- did the worker exit normally?
- did the host disappear?
- did the application restart while the lease was still marked running?
- is a persisted running record now orphaned?

Use architecture-appropriate evidence such as:

- heartbeat / lease timestamp
- owning runtime/process identity
- explicit release on normal shutdown
- periodic stale lease reconciliation
- worker completion events
- host lifecycle reconciliation

The exact representation is up to the current architecture.

Requirements:

1. Opening a conversation must not be necessary to correct its state.
2. Closing/switching away from a conversation must not stop liveness tracking.
3. A dead worker must eventually be reconciled without operator navigation.
4. A genuinely alive long-running worker must stay alive even beyond the previous five-hour window when heartbeat/liveness evidence remains fresh.
5. A fast application restart after a worker dies must not preserve a fresh-but-dead `running` lease indefinitely.
6. Graceful shutdown should release/reconcile owned work where safe.
7. A periodic bounded reaper/reconciliation path must exist so stale leases are not checked only once at startup.
8. Multiple reconciliation paths must not race a completed worker back into running state.

Relevant source areas from current evidence/audit include:

- `packages/ui/src/zaicode/zaicodeStall.ts`
- session-index projection
- live-run projection
- conversation/composer live publication
- `packages/services/src/zaicode/zaicodeJobService.ts`
- `packages/services/src/zaicode/zaicodeJobRepo.ts`
- `zcodeTaskServiceAdapter.ts`
- runtime/desktop host lifecycle

Revalidate exact paths against the current source before editing.

TESTS

Add behavioral tests for at least:

- foreground worker completes while its conversation is not open
- background worker completes while another project is selected
- fresh running worker remains running
- worker older than five hours with fresh heartbeat remains running
- stale persisted `running` record becomes non-running/recoverable
- application restarts shortly after worker death
- graceful host shutdown
- ungraceful host disappearance
- repeated reconciliation is idempotent
- opening the conversation does not change truth, only presentation

Acceptance:

The same canonical runtime state must be observable before and after opening the project.
