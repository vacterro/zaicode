## 2. F1 — Auto Goal: a completed goal is not a replaceable lifecycle (repaired)

- **Severity**: P2 now / P1 latent (the moment any owner wires `mayContinueZaicodeGoal`,
  the second task in a session can never be classified as open).
- **User impact**: with Auto Goal ON, two different prompts in one session collapse onto
  one intent. Every prompt without an explicit `/goal` composes the objective
  `"cc all"` (`withZaicodeAutoGoal` appends `/goal cc all`,
  `zaicodeGoalObjectiveOf` reads it back), and the intent id is
  `project :: session :: objective`. After the first goal reaches `complete`, the next
  user submission returns that same terminal intent (`created:false`,
  `outcome:"complete"`), so the new run is born terminal and inherits the previous run's
  spent continuation budget. The composer readout loses its goal line entirely
  (`zaicodeGoalLiveIntent` filters terminals) and the continuation decision answers
  "the goal is complete".
- **Root cause**: `packages/ui/src/zaicode/zaicodeGoalSupervisor.ts:102`
  `if (existing && !(existing.stopped && input.fresh))` — the terminal-replacement clause
  names one terminal state out of two. `stopped` is replaceable by a fresh submit,
  `complete` is not, although both are `isZaicodeGoalTerminal`.
- **Reproduction** (run before the patch, zcode/packages/ui):
  probe output —
  `objective(p1) = "cc all"`, `objective(p2) = "cc all"`,
  `task two created: false outcome: complete`,
  `mayContinue(task two): { send: false, reason: 'the goal is complete' }`,
  `fresh submit after a spent+completed goal -> created: false continuations: 20`.
- **Why existing tests missed it**: `packages/ui/test/zaicodeT222GoalSupervisor.test.ts`
  covers resubmit-while-live (`created:false`) and resubmit-after-**stop**
  (`fresh` ⇒ `created:true`), but never resubmit-after-**completion**. The completed
  path is asserted only in the other direction (a completed goal leaves supervision).
- **Repair**: the clause now asks `isZaicodeGoalTerminal(existing.outcome)`, so a fresh
  user submission replaces *any* terminal lifecycle (new `seq`, `continuations: 0`,
  `outcome:"active"`); a live lifecycle is still never replaced, so
  "resubmit cannot fork one goal" is unchanged. Doc block updated.
- **Regression test**: `T-222 audit: a new user submission after a completed goal starts
  a fresh lifecycle` appended to `packages/ui/test/zaicodeT222GoalSupervisor.test.ts`
  (covers: created, non-terminal, budget reset, live-intent still deduped,
  repeatable complete→submit→complete→submit).
- **Red control**: the clause was reverted to `existing.stopped`; the new test failed
  (`AssertionError: a new user action after a completed goal is new work`);
  the file was restored from backup and the count of the repaired clause re-verified.
- **Residual risk**: `continuations` is inherited across a *paused/blocked* lifecycle
  (neither is terminal, and neither is replaced) — intended, but only correct while the
  budget is per-intent rather than per-run. Single-session identity is unchanged;
  if an owner is later wired to `mayContinueZaicodeGoal`, the id scheme
  (`project::session::objective`) still cannot distinguish two same-objective prompts,
  so the replacement rule is load-bearing.

## 3. F2 — Auto Retry split brain on the queue auto-resume owner (repaired)

- **Severity**: P2. False UI truth plus an unwanted autonomous send, and in the other
  direction a lost autonomous resume.
- **User impact**, both reachable from the shipped controls:
  1. session auto-continue explicitly `On` + retry preference off in every scope
     (global/project/session): the composer's Auto Retry button and tooltip read
     "Auto retry off · global retry preference is off", yet a queue paused by an error
     resumed by itself (`zaicodeMayAutoSend` returns true for `mode:"on"` regardless of
     the feature flag — asserted as intended in `zaicodeSrc82Retry.test.ts`).
  2. global `autoRetry` OFF with an explicit per-project `ON`: the button in that project
     reads ON ("This project"), but the queue never resumed, because the old gate read the
     GLOBAL flag only (`featureOn = state.autoRetry`).
- **Root cause**: two answers to one question inside one policy module.
  `zaicodeRetryPolicy.zaicodeMayAutoSend` (session-On wins, needs master AND feature
  otherwise) vs `zaicodeRetryPolicy.zaicodeEffectiveAutoRetry` (documented as the
  "single effective projection for every retry owner and representation", requires the
  project/session-aware preference). Three owners asked the second one
  (`zaicodeAutoRetry`, `zaicodeTurnRetryWatch`, `zaicodeCrashResume`);
  `zaicodeQueueAutoResume` asked the first, with a global-only feature flag.
- **Reproduction**: source call-chain read plus the focused assertions below; the
  pre-fix behaviour is asserted in the new test as a positive control
  (`zaicodeMayAutoSend({mode:"on",masterOn:true,featureOn:false}) === true`).
- **Why existing tests missed it**: `zaicodeSrc81Queue.test.ts` tested only the pure
  `zaicodeQueueMayAutoResume` facts and a source-regex on `SessionPane`; the *gate* the
  hook composed was never asserted, and the `zaicodeMayAutoSend` matrix test
  (`zaicodeSrc82Retry.test.ts`) positively pins the divergent answer for the
  auto-continue use, so nothing compared the two owners.
- **Repair**: `packages/ui/src/zaicode/zaicodeQueueAutoResume.ts` now gates through a new
  pure `zaicodeQueueAutoSendAllowed` that calls `zaicodeEffectiveAutoRetry`; the hook takes
  a `projectKey` (the pane passes `workspaceKey`); `zaicodeEffectiveAutoRetry`'s `prefs`
  parameter is narrowed to the exported `ZaicodeAutoRetryPrefs` slice so the hook can build
  it from selectors (type-only widening — every existing caller still typechecks).
  The conservative direction was chosen deliberately: the operator's explicit OFF wins.
- **Regression tests**: `audit: the queue asks the same effective retry projection as
  every other automatic send` and `audit wiring: the hook gates on the projector and the
  pane names the project` in `packages/ui/test/zaicodeSrc81Queue.test.ts`
  (session-On-vs-preference, per-project ON visible, enabled/halt/session-Off/master-off
  unchanged, session-On still self-continues when the preference allows).
- **Red control**: `zaicodeQueueAutoSendAllowed` was reverted to the old
  `zaicodeMayAutoSend` composition; both new tests failed; the file was restored from
  backup and the repaired call re-verified.
- **Residual risk**: the crash resume still asks `zaicodeMayAutoSend` with
  `featureOn = prefs.resumeAfterCrash` and `zaicodeAutoSendAllowed` is now unused in
  production. They are *auto-continue* owners, so their session-On precedence is the
  documented older rule, not this defect. If that rule is ever unified, those two call
  sites must move in the same change.

## 3b. F6 — Save All IPC boundary accepted any shape (repaired)

- **Severity**: P3 (hardening). Reachable only by a renderer-side bug, but the file it
  writes is a *shipped default*, so the blast radius is a released build rather than one
  profile.
- **User impact / exposure**: `zaicode:save-settings-snapshot` is a platform IPC handler
  (`packages/desktop/src/main/desktopMainIpcPlatform.ts:459`) that takes an arbitrary JSON
  string from the renderer and, on success, writes it to
  `packages/ui/src/zaicode/zaicodeSettingsDefaults.json` in the developer's checkout, which
  the next build bundles and seeds into empty storage. The only checks were a 4 MB size cap
  and `JSON.parse` returning something object-shaped, so any renderer-side defect (or a
  compromised renderer) could persist arbitrary keys, nested objects or non-string values
  as a released default. No credential path was found: the renderer allowlist carries no
  secrets, so this is not a leak.
- **Root cause**: no shape validation at the renderer→main boundary; the reader
  (`readZaicodeSetting`) depends on `version: 1` plus flat `settings`/`cueAudio` string
  maps, and nothing enforced that. There was also no test of the writer at all — the only
  coverage was a renderer-side source check in the T-223 suite.
- **Reproduction of the gap**: the renderer payload is exactly
  `{version:1, settings, cueAudio}` (`captureZaicodeSettingsSnapshot`), passed through
  unchanged by `ZaicodeSettingsSection.tsx:103-104`; before the repair, any other shape
  that parsed as an object was written verbatim.
- **Why existing tests missed it**: the desktop suite never imported this module (main
  modules that import `electron` are covered by source-text assertions elsewhere), and the
  UI-side T-223 test only checks that the UI calls the writer on the success branch.
- **Repair**: new pure module
  `packages/desktop/src/main/zaicodeSettingsSnapshotShape.ts` validates schema version,
  flat string maps, the `zaicode-*` key namespace, key length and bounded entry counts; the
  writer consults it before it serialises anything and returns `ok:false` with a reason
  instead of writing.
- **Regression test**: `packages/desktop/test/zaicodeSettingsSnapshotShape.test.ts`
  (4 tests) exercises the decision directly — a real snapshot and its legitimate variants
  pass; 14 malformed payloads are refused with a reason; the caps and the key-length rule
  are boundary-checked; one wiring assertion proves the gate runs before serialisation.
- **Red control**: (a) the validator was made permissive — two behavioural tests went red;
  (b) the writer's gate was reverted to the old object-only check — the wiring test went
  red. Both files restored from backup, re-verified green, and the gate line re-counted.
- **Residual risk**: the renderer's own allowlist is still not enforced in main (it cannot
  be imported across the bundle boundary), so a snapshot can carry a `zaicode-*` key the
  renderer does not produce. That is harmless — `readZaicodeSetting` only answers for keys
  something actually reads — and the T-223 coverage test keeps the renderer list honest.

## 5b. Strong negative evidence — areas that look robust

These were attacked and did **not** yield a defect; they are stated so a later audit does
not spend its budget re-deriving them, and so "no finding" is not mistaken for "not
looked at".

- **Save All / durable settings** (T-228's hypothesis): all 55 allowlist keys were traced
  to a reader that goes through `readZaicodeSetting`. No dead entry remains; the earlier
  three-site hole was closed under T-227. Deliberately corrupted persisted values
  (missing key, `null`, wrong type, truncated JSON, unknown enum) degrade to defaults
  through 29 guarded `try/catch` load paths.
- **Router ownership**: the supervisor is a single serialised owner (`#exclusive`, `#tail`,
  `#inflight`) with a generation fence; `attempts` is persisted *before* the recovery
  action so a restart cannot replay it, and the response budget is bounded at 10 with the
  backoff capped. The connection-presence projector is genuinely wired
  (`zaicodeRouterHost.ts:244` emits `supervisor: supervisor.state`; the renderer type
  declares the same fields), so it is not a projection reading fields nobody writes.
- **Retry persistence and attempt budget**: one shared `attemptsBySession` map across the
  pane countdown and the background host, each re-asking the gate at fire time, with the
  `localPanes` claim retiring the background watch — no double-fire path was found.
- **Composer fit**: quantised measurements, release-only hysteresis, skip-when-equal DOM
  writes and `rAF`-coalesced observer callbacks; no oscillation cause remained in the
  source (real breakpoints still need the packaged app).
- **Side-pane identity and restart**: the in-memory memory map is process-local, so the
  persisted policy wins after restart rather than shadowing it; owner keys are
  session-or-`__draft__@workspace`, and corrupt persisted policy normalises.
- **Secrets**: no credential, token or account-registry field is reachable from the
  ZAICODE preference stores or the Save All allowlist.

## 10. F8/F9 — the translation staleness signal (found by the `ee` producer, 2026-10-06)

Neither finding is a zcode source defect, so neither carries a red control over product
behaviour; both were measured from the source of the consumer, not from the producer's
claims.

**F8, measured.** `phases/translate.md` defines the marker as the digest of the current
`README.md` with version strings normalised out, and `validate.py:8391` computes it once as
`source_content_digest(README.md read with read_text(encoding="utf-8-sig"))` — text mode,
so CRLF folds to LF. The producer that stamped these surfaces hashed raw Node bytes
instead, CRLF intact. On this CRLF checkout the two recipes can never agree:

- validator path, current `README.md` (clean at HEAD, `3f74596a`): `783b916d4bee01ac`
- the same function over CRLF-preserving bytes: `c06a2e2bdf29a4e7`
- the last-translated revision `26dcd83f`: `55988370392b3999` under the validator path,
  `bdae0fb3f831bca1` raw-byte — and `bdae0fb3f831bca1` is exactly the value on all 35
  product surfaces.

Two errors were live together: a recipe the consumer cannot reproduce, and a source
revision older than the marker claimed. The whole `README.md` diff `26dcd83f..3f74596a`
is the release badge — one added `**v0.0.2**` line and the badge URL `0.0.1` -> `0.0.2` —
so no translatable prose moved and no locale needed re-translating; only the signal was
false. Repaired for the 30 producer-owned surfaces by the `ee` run (SAIT-002 package
`sha256:305d7e05`, `READY/` payload plus a ready OUTBOX entry, independent gate
`kitchen/_verify_restamp.py` exit 0 with a 4-mutation red control). Residual: the five
Core-owned surfaces `docs/locales/{ru-RU,et-EE,ded}/README.md`, `README.ee.md` and
`README.ded.md` still carry `bdae0fb3f831bca1` and still fail `digest_marker_matches`.

**F9, measured.** `release_contract.locale_readme_paths` returns
`kitchen/<dir>/README_<dir.upper()>.md` for every directory of the given kitchen. In this
project the translation kitchen's subdirectories are named after surfaces — `cli, docs,
drafts, extras, integration, integration-workspace, outbox, payload` — not after locales,
so the gate would read `kitchen/cli/README_CLI.md` as though `cli` were a language, while
the real locale surfaces live in the product at `docs/locales/`. All eight kitchen guides
carry no `source-digest` marker at all. Two readings are possible (the kitchen should hold
per-locale READMEs, or the enumeration should be taught this layout) and both are
Core/SAIPEN-side decisions, so this ledger reports rather than repairs it. Measurement
caveat: `validate.py` derives `_tools_parent` from its own location, so a run from this
project evaluates the SAIPEN home's kitchen and README, never this project's — F8's digest
was therefore proven by calling the engine function and the predicate directly, which is
the strongest check available here.
