## Why publication stopped

`saipen ship` plans a **v0.0.2** release: a workspace version bump across roughly 40
README/CHANGELOG files plus a `v0.0.2` tag push to `origin`. That is a release decision,
not a routine branch push, and no approval was given.

Two paths were checked and rejected:

- **`mode: no-publish`** — `saipen_engine/capability.py` reads it from a host-declared
  environment variable. The session negotiated `full`. Self-declaring a host capability
  is not an agent decision.
- **Narrower push** — `saipen push` re-enters the same SHIP path; there is no
  branch-only variant, and ship.md step 6b couples the version bump, commit, push and tag.

`saipen ticket done T-179 --closure-mode own_patch --dry-run` returns `FINISHED`, so the
ticket is one authorised command from DONE. Closure and publication are **separate**
operations, which is exactly why it was not closed: DONE with the fix sitting uncommitted
in a staging area would record a completion no commit or remote ref backs.

## The first-publish gate was a false positive

STATE carried `WAIT: first-publish` while its own classifier disagreed:

```
$ python -c "from saipen_engine.release import _push_endpoint,_remote_snapshot; ..."
push_endpoint = 'https://github.com/vacterro/zaicode.git'
query_ok      = True
ref_count     = 8
CLASSIFICATION= ('ESTABLISHED', '')
```

`release.py:1337` sets `first_publish_wait = cls in (REMOTE_ABSENT, REMOTE_EMPTY)`.
`ESTABLISHED` is neither, so the gate could not have fired. Filed as **T-184** and the
stale blocker cleared with `saipen recover resolve-blocker`. Remote is unchanged:
`refs/heads/zaicode` = `4f6fbef4` = local `HEAD`.

## Gotcha worth keeping

`saipen_engine/log.py` `_claims_failure` scans free text for any nonzero count before a
`FAIL` token. VERIFY evidence reading `7 fail / 0 pass` was rejected as a failure claim —
the guard read proof of a passing red control as a failed cycle. Writing `0 of 7 passing`
is accepted. This is the "Narrative Authority Leakage" class its own docstring describes.
