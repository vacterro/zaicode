## A3 P1 follow-up — overlay monitor placement (b54ecc9, 2026-09-27)

After 4434ac4 (readiness feed) the operator still reported FAIL: ProTrail
"appears on the other side, but still does not work on all three monitors"
(E-1588). The readiness race was fixed, so the surviving defect is downstream
of the state feed. Product commit `b54ecc9` "fix(protrail): keep overlays on
their monitors" addresses the remaining WINDOW_PLACEMENT cause.

### Proven cause and change

The overlay `BrowserWindow` was a normal (frameless, `skipTaskbar`) window.
On Windows, a normal new window is relocated to the active monitor by desktop
window managers (FancyZones / PowerToys "launch new windows on the active
monitor"), *after* the overlay is shown at its per-display bounds. Three HWNDs
existed, but two or three could land on the same physical monitor — matching
the operator's "appears on the other side" report. `skipTaskbar` alone does
not stop this; the fix classifies the overlay natively:

```
// packages/desktop/src/main/zaicodeProtrailGlobal.ts, createOverlay()
...(process.platform === "win32" ? { type: "toolbar" } : {}),
```

A `type: "toolbar"` window is a native tool window that desktop managers do
not treat as a normal new window, so it stays on the display its bounds place
it on. Non-Windows platforms keep their existing window type. Bounds remain
owned by the display map; no arbitrary offset, no hardcoded topology, no
renderer geometry compensation. The behavior is documented in
`specs/protrail-overlay-readiness.md`.
